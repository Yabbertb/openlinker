## [0.21.0](https://github.com/Yabbertb/openlinker/compare/v0.20.0...v0.21.0) (2026-11-26)


###   BREAKING CHANGES

* **sales-documents:** POST /fiscal-registrations now answers 202 Accepted with AcceptedFiscalRegistrationResponseDto instead of 200 with FiscalRegistrationResponseDto. Callers must poll the registration-status read to learn the outcome.
* **oms:** the `locationId` propagation skip is retired ([#2324](https://github.com/Yabbertb/openlinker/issues/2324)). An inventory write naming a `locationId` now propagates to marketplaces; previously it logged `inventory_write_propagation_skipped_non_default_location` and enqueued nothing, so the channel kept whatever a pooled write last sent. No adapter in this repository is affected  WooCommerce and PrestaShop both emit `locationId: undefined`. Only an in-house or out-of-tree `InventoryMaster` adapter returning a real `locationId` changes behaviour; such connections have had their channel stock silently frozen, and their next write publishes the true aggregate, possibly as a large single-step correction in either direction. Opt out per adapter by returning `locationId: undefined`. Full procedure and the detection query: `docs/operations/inventory-location-propagation.md`.
* **web:** POST /fiscal-registrations now answers 202 Accepted with AcceptedFiscalRegistrationResponseDto instead of 200 with FiscalRegistrationResponseDto. The endpoint's own Swagger description previously told callers to read `status`/`failureMode` from the response body to learn the registration outcome - those fields no longer exist on the response. Callers must instead poll the registration-status read (GET .../registration-status) to learn the outcome.
* **orders,fiscalization,sales-documents,web:** POST /fiscal-registrations now answers 202 Accepted with AcceptedFiscalRegistrationResponseDto instead of 200 with FiscalRegistrationResponseDto. The endpoint's own Swagger description previously told callers to read `status`/`failureMode` from the response body to learn the registration outcome - those fields no longer exist on the response. Callers must instead poll the registration-status read (GET .../registration-status) to learn the outcome.
* **core:** `SYNC_JOBS_EVENT_STREAM` is no longer exported from `@openlinker/core/sync`. The `events.sync.jobs` stream it named is a ghost - nothing reads it, verified as having no remaining in-tree consumers - and the upgrade deletes it. Separately, Redis now runs with `maxmemory` set together with `maxmemory-policy noeviction`, so an existing deployment already holding more data than the new limit will reject every `denyoom` command, including `XADD`, until the previously-unbounded streams are trimmed. `XTRIM` is not a `denyoom` command, so it stays available and is the way out. Run, in order: `DEL events.sync.jobs`; `XTRIM events.inbound.webhooks MAXLEN ~ 50000`; `XTRIM events.inbound.webhooks.dead MAXLEN ~ 10000`; `XTRIM jobs.sync MINID ~ {epoch_ms_14_days_ago}`; `XTRIM events.master.deletion.dead MINID ~ {epoch_ms_30_days_ago}`. Then confirm with `CONFIG GET maxmemory`, `CONFIG GET maxmemory-policy` and `INFO memory`. Full procedure, sizing guidance for `REDIS_MAXMEMORY`, and the rationale for `noeviction`: docs/operations/redis-stream-retention.md (refs #2163, #2223, #2226)
